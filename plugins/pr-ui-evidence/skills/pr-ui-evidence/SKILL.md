# PR UI証跡（before/after）

PRの変更が画面にどう影響するかを、レビュアーが一目で確認できるbefore/afterのスクリーンショットとして残す。**撮影と整理が役割で、見た目の良し悪しの判定はしない**（判定が必要なら`ui-verify-loop`を使う）。

## 前提

- 対象プラットフォームの操作スキル（Android: `android-emulator-operate`、iOS: `ios-simulator-operate`）が使えること。操作方法・サンドボックスの扱い・未導入時の案内はそれらに従い、ここでは重複して定義しない。
- `git`と`gh`が使えること。作業ツリーに未コミットの変更がある場合は、ブランチ切り替えで失われないよう、先にユーザーへ確認する。
- アプリのビルド・起動方法はプロジェクトごとに違う。READMEやCLAUDE.md/AGENTS.mdを見ても分からなければ、ユーザーに聞く。

## 手順

### 1. 対象PRと比較元を決める

- PR番号またはブランチが指定されていなければ、現在のブランチのPRを`gh pr view --json number,baseRefName,headRefName,url`で調べる。無ければユーザーに聞く。
- 比較元（before）は、PRのベースブランチ（`baseRefName`）の**先端ではなく、PRのブランチとのmerge-base**にする。ベースが進んでいると、PRと無関係なUI変更がbeforeに混ざるため。
  1. `git fetch origin <baseRefName>`、`gh pr checkout <PR番号>`でPRのブランチを取得する（forkからのPRでも動く。ローカルのbase/headは古い・無いことがある）。
  2. `git merge-base origin/<baseRefName> HEAD`で得たコミットを`<base>`とする。afterはPRのブランチ（`HEAD`）。

### 2. 影響する画面を推定する

1. `git diff --name-only <base>...HEAD`で変更ファイルを一覧する。
2. UI以外（ロジック・テスト・CI・ドキュメントのみ）の変更で、見た目に影響しないと判断できれば、**その旨をユーザーに伝えて終了する**。無理に撮らない。
3. UIに関わる変更ファイル（画面・ウィジェット/ビュー・レイアウト・テーマ・文言/リソース・画像）から、**影響する画面を最大5つ程度の候補**に絞る。共通部品やテーマの変更は影響範囲が広いので、代表的な画面に絞る。
4. 候補と、各画面に到達する操作手順（タップ順・必要な状態）を**ユーザーに提示して確認する**。到達手順が分からない画面は推測せず聞く。確認が済むまで撮影に進まない。

### 3. 撮影する（before → after の順）

プラットフォームごとに、固定の条件で撮る。条件が違うと差分がノイズになる。

- 同じ端末・同じOS・同じ向き・同じ言語/外観モード（ライト/ダーク）を使う。
- 毎回アプリを初期状態から起動し、同じ手順で同じ画面へ到達する。データが日時などで変わる場合は、その旨をメモする。
- 保存先は`.gitignore`済みのディレクトリ（例: `work/pr-evidence/<PR番号>/`）。無ければユーザーに確認する。ファイル名は`<画面名>_before.png` / `<画面名>_after.png`。

手順:
1. `git switch --detach <base>`（またはworktree。`<base>`は手順1のmerge-baseコミット）→ ビルド・インストール・起動 → 各画面へ到達してスクリーンショットを`*_before.png`として保存。
2. `git switch -`でPRのブランチへ戻る → 同様に`*_after.png`を保存。
3. 作業前のブランチ（`gh pr checkout`する前のもの）に戻す。

ベース側にその画面が存在しない（新規画面）場合、`before`は「なし（新規）」とする。

### 3.5. 変更の有無を判定する（Decision AI。任意。条件を満たすときだけ）

画面ごとに、before と after が「実質的に変わっているか」を、目視の代わりにOpenAI Decisions APIで判定できる。**次の2つが両方そろったときだけ**使い、そろわなければこの手順を飛ばして、自分で2枚を見比べる（従来どおり）。

1. 環境変数`DECISION_AI`が`1`（`true`/`on`/`yes`も可）。利用者がプロジェクトの`settings.json`の`env`で有効にする。
2. 環境変数`OPENAI_API_KEY`が設定されている。キーはリポジトリの外に置くもので、このスキルは値を扱わない。

#### APIキーの確認方法（厳守。キーが会話・ログ・学習に流れないようにする）

存在確認は、次のコマンド**だけ**で行う。値には一切触れず、結果は終了コードと固定の文言で返る。`SCRIPTS`は、このSKILL.mdがあるディレクトリの`scripts/`を絶対パスにしたもの（スキルの読み込み時に示されるベースディレクトリで解決する）。

```bash
python3 -I "$SCRIPTS/decide.py" --check; echo "exit=$?"
```

| exit | 意味 | 対応 |
|---|---|---|
| 0 | 使える | 下の判定へ進む |
| 10 | `DECISION_AI`が無効 | 何も言わずこの手順を飛ばす（異常ではない） |
| 3 | 有効だがキー未設定 | ユーザーに伝え、使わずに進めてよいか確認する。設定方法は案内してよいが、**値は聞かない・貼らせない** |

**やってはいけないこと**: `env`・`printenv`・`export -p`・`set`・`declare -p`の実行、`echo "$OPENAI_API_KEY"`、キーの一部の表示、`.env`・`.envrc`・`~/.zshrc`・`settings*.json`を読んでキーを探すこと、`set -x`、キーをコマンドライン引数に渡すこと、キーの値・長さ・一部を返答やファイルに書くこと。`decide.py`が失敗したときは、リクエスト本文を出して原因を探らず、終了コードと1行のメッセージだけで判断する。

#### 判定の手順

1. 画像を標準サイズに正規化して、**リポジトリの外**（`$TMPDIR`）に作る（トークンを減らすため。元の画像は変更しない）。

   ```bash
   bash "$SCRIPTS/normalize-image.sh" work/pr-evidence/<PR番号>/<画面名>_before.png "$TMPDIR/<画面名>_before-norm.png"
   bash "$SCRIPTS/normalize-image.sh" work/pr-evidence/<PR番号>/<画面名>_after.png "$TMPDIR/<画面名>_after-norm.png"
   ```

2. 判定する。`$SKILL_DIR`はこのSKILL.mdがあるディレクトリ。**画像のラベルは、質問文が参照している`before(変更前)`と`after(変更後)`のままにする。**

   ```bash
   python3 -I "$SCRIPTS/decide.py" --profile pr-change \
     --questions "$SKILL_DIR/decision/change-questions.json" \
     --image 'before(変更前)='"$TMPDIR/<画面名>_before-norm.png" \
     --image 'after(変更後)='"$TMPDIR/<画面名>_after-norm.png"
   ```

3. **`summary.next`だけで分岐する**（確率を自分で読んで決めない）。

   | `summary.next` | 扱い |
   |---|---|
   | `changed` | 変更あり。証跡に載せ、何が変わったかは、画像から**実際に見える差分**だけを書く（手順4） |
   | `unchanged` | 変更なしの可能性が高い。**証跡から画面を外さない。** 「変わっていない（自動判定）」と明記して載せる |
   | `check` | 決められない（別の画面に見える・曖昧・回答拒否など）。自分で2枚を見て決める |

   `decide.py`が0以外で終了した場合も、自分で2枚を見て決める。ただし、終了コード7（before と after の画像のサイズが違う）のときは、手順1の`normalize-image.sh`で両方を同じ標準サイズにそろえて、もう一度実行する（手順1のとおり、判定の前に両方を正規化していれば起きない）。それでも7なら、自分で見て決める。

4. **「変更なし」の判定を、画面を省く根拠にしない。** 変化の見落としが最も困る失敗なので、`unchanged`でも載せて、「自動判定であり、目視で確認していない」ことが分かるようにする。ベース側にその画面が無い（新規画面）場合は、この判定を行わない。
5. 画像がOpenAIに送られる。スクリーンショットに個人情報・秘密情報が写っていることが分かっている画面は、送らずに自分で確認する。サンドボックスで`api.openai.com`に通信できない（終了コード4）場合は、許可を依頼するか、自分で確認する。個人情報の写り込みの確認は、この判定とは別に、従来どおり公開前に行う。

### 4. 証跡のMarkdownを作る

`work/pr-evidence/<PR番号>/evidence.md`に、PR説明文へそのまま貼れる形で書く。

```markdown
## UI の変更(before / after)

撮影条件: <端末> / <OS> / <ライト|ダーク> / <言語>

### <画面名>(<到達手順>)
| before | after |
|---|---|
| ![before](<画像URL>) | ![after](<画像URL>) |
```

- 画像のURLは手順5で確定する。確定までは相対パスのプレースホルダにしない（壊れたリンクを貼らないため）。
- 見た目が変わっていない画面は、変わっていないと明記して載せるか、載せない。変化があるかのように書かない。手順3.5で`unchanged`と判定された画面は、外さずに「変わっていない（自動判定）」と書いて載せる。
- 「何が変わったか」の説明は、スクリーンショットから**実際に見える差分**だけを書く。コードから想像した差分を書かない。

### 5. 画像のホスティングとPRへの反映（外部への公開なので確認する）

`gh`にはPR本文へ画像を直接アップロードする機能がない。次のどれにするかを**ユーザーに確認してから**実行する。リポジトリが公開の場合、画像も公開される点を伝える。

| 方法 | 内容 |
|---|---|
| 専用ブランチへコミット | `pr-evidence`のようなorphanブランチに画像だけをpushし、raw URLで参照する。公開リポジトリでは誰でも見られる。非公開リポジトリのraw URLはログイン中の閲覧者にだけ表示される |
| PRコメントに手動添付 | 画像をGitHubのWeb UIでコメント欄にドラッグ&ドロップしてもらう。こちらでは自動化できない |
| 画像は載せない | ローカルの`evidence.md`と画像を渡すだけにする |

PR本文の更新は`gh pr edit --body`で上書きする前に、現在の本文を取得して**既存の本文を残したまま**証跡セクションを追記（既に同じ見出しがあれば置換）する。実行前に最終的な本文をユーザーに見せて確認を取る。

## 注意

- スクリーンショットに個人情報・秘密情報（メールアドレス、トークン、本番データ）が写っていないか、公開前に確認する。写っていたら載せない。
- 撮影できなかった画面（到達不能・ビルド失敗など）は、確認済みとして扱わず、証跡に「未撮影」と理由を明記する。
